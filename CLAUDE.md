# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Dispatch Watch** — a Windows Forms application (C# / .NET 4.0) used by ASL Aviation Group flight dispatchers to download, filter, classify, and report on ICAO NOTAMs. Built and maintained in **SharpDevelop portable** — Visual Studio is not available.

## Repo layout

The solution file sits at the repo root; the project and all sources live in a `Dispatch Watch/` subfolder:

```
Dispatch Watch.sln            ← repo root (open this)
Dispatch Watch/               ← project subfolder
   Dispatch Watch.csproj
   MainForm*.cs, Program.cs, icon.ico, …
CLAUDE.md
```

The compiled output is `Dispatch Watch.exe` (`<AssemblyName>`); the window title and `<ApplicationIcon>` (`icon.ico`, a crossing-runways mark) are also "Dispatch Watch".

`Dispatch Watch.sln` / `Dispatch Watch.csproj` is the **only** solution/project — open the one at the repo root. A stray second solution/project (e.g. an older `ICAO-CSV.sln`/`ICAO-CSV.csproj`, created once when setting up a second SharpDevelop machine) is a leftover, not a real second target: it silently omits whatever `.cs` files hadn't been added to it yet, so anything built against it looks like missing features rather than a build error. Delete it rather than maintaining two `.csproj`s in parallel.

## Build & Run

Open `Dispatch Watch.sln` in SharpDevelop. Build with **F8**, run with **F5**.

There are no automated tests, no lint tools, and no CLI build commands — SharpDevelop is the only build environment.

**Close any running `Dispatch Watch.exe` before building** — SharpDevelop can't cleanly overwrite a locked exe/DLL while an instance is running (including the same dispatcher's own local copy, `EnsureLocalInstall`'s target), which can leave a partial/corrupt build output. That surfaced in practice as a startup crash pointing at `Stations_ICAO_IATA`/`OCC.mdb` that looked like the OneDrive-`LastWriteTime` issue documented below, but was actually just a bad build from building over a running instance — closing the app first and rebuilding resolved it.

**Runtime requirements:**
- Windows only (WinForms + OleDb)
- `wkhtmltopdf.exe` must be placed next to the compiled `.exe` for PDF export to work
- One Access database must be present at runtime: `ICAO_storedNotams.mdb` — NOTAMs, filter results, impact classification, the Flight Schedule cache, and (since the `OCC.mdb` → `ICAO_storedNotams.mdb` migration, see below) station mapping (`Stations_ICAO_IATA`: ICAO ↔ IATA, operator types, RWY memo), `Runways`, and `Notams_ICAO_CSV`. There used to be a second `OCC.mdb` holding those three tables — it had no sync of its own (unlike `ICAO_storedNotams.mdb`'s `StartApp`/`EndApp`), which is what caused a fresh local install under the multi-user deployment model to crash on startup missing it entirely. `EnsureOccMigrated()` (`MainForm.Deployment.cs`) folded it in once and for all instead of patching around the gap.
- Network access to the fleet's flight-planning web services (`FlightScheduleService.svc`/`BriefingService.svc`) is required for the Flight Schedule tab; base URLs are configurable on the Admin tab (`ArchiveConfig.xml`, auto-created on first run)

### Multi-user deployment (`MainForm.Deployment.cs`)

Rolling out to ~10 dispatchers on top of the existing "download DB from V: at startup, upload at close" model (`StartApp`/`EndApp`, `MainForm.cs`) needed five things the original single-user design had none of — all run from the `MainForm` constructor, before `StartApp()`'s DB download:

- **Local install + auto-update**: `EnsureLocalInstall()` — if `Application.StartupPath` isn't already `%LOCALAPPDATA%\Dispatch Watch\` (a dispatcher's first run, typically via a manually-placed "Install Dispatch Watch" shortcut on V: that just launches the existing V:-hosted exe), it copies the app files to that local folder (`CopyAppFiles`, everything except `.mdb`/`.lock` and a handful of session/config files — `.mdb` is skipped unconditionally since `ICAO_storedNotams.mdb` is `StartApp`/`EndApp`'s job entirely, not this method's), creates a Desktop shortcut via late-bound `WScript.Shell` COM (`CreateDesktopShortcut`, same `Type.GetTypeFromProgID`+reflection idiom as the Outlook automation below — no new project/COM reference needed), then relaunches (`Process.Start` with an explicit `WorkingDirectory`, not the bare-string overload, so the new process's CWD is never left to inherit-and-guess) and `Environment.Exit(0)`s. If already local, the same method instead compares `File.GetLastWriteTime` on the V: exe vs the local one (same idiom `StartApp`/`EndApp` already use for the DB) and re-copies + relaunches when V: is newer. Either branch that does work never returns to the constructor. `LogDeploy()` traces every branch/decision to `deploy_log.txt` next to the exe — this method's `Environment.Exit` calls bypass `Program.cs`'s crash logger entirely (an `Exit` is not an exception), so a silent-exit bug here would otherwise leave zero trace, the same failure shape as "taskbar icon flashes then vanishes" with no dialog. `StartApp()`/`EndApp()` (`MainForm.cs`) also log every timestamp comparison and download/no-download/upload decision via the same `LogDeploy()` — they used to only report success/failure through blocking `MessageBox`es on every single launch, easy to miss or reflexively dismiss, and gave no durable record to check after the fact.
- **`%LOCALAPPDATA%`, not `Documents`**: the local install folder is deliberately `Environment.SpecialFolder.LocalApplicationData`, not `MyDocuments` — on this fleet, `Documents` is OneDrive-redirected (Known Folder Move) for most users, and OneDrive's sync client is known to touch a local file's `LastWriteTime` independently of any real write to it. That silently broke `StartApp()`'s "is the local copy newer-or-equal than V:?" freshness check: it kept concluding a stale, pre-`OCC.mdb`-migration local `ICAO_storedNotams.mdb` was "already up to date" and never re-downloaded the real one, crashing on the missing `Stations_ICAO_IATA` table every launch. `%LOCALAPPDATA%` is explicitly meant for non-roaming, machine-local app data and is never OneDrive-synced, sidestepping the whole class of problem for a frequently-rewritten binary Access file. A dispatcher whose local install already exists under the old `Documents`-based path self-heals automatically — the next launch's `alreadyLocal` check no longer matches, so it's treated as a fresh "first run" into the new `%LOCALAPPDATA%` location (one extra relaunch hop, no manual cleanup needed).
- **`EnsureOccMigrated()`**: one-time migration folding the old `OCC.mdb` (`Stations_ICAO_IATA`/`Runways`/`Notams_ICAO_CSV`) into `ICAO_storedNotams.mdb`, via Jet's cross-database `SELECT * INTO [table] FROM [table] IN 'OCC.mdb'` (imports structure + data in one statement per table, no hand-rebuilt schemas). Runs against the shared V: files directly (`VAppFolder`, not `Application.StartupPath`) so it takes effect exactly once for every dispatcher regardless of who launches first or from where, called at the very start of the constructor — before `EnsureLocalInstall()`, which may relocate the process off V: and never return. Idempotent (a `SELECT TOP 1 * FROM Runways` probe against the target first; any success means "already migrated, skip") and left in permanently rather than removed after the first run. This replaced an earlier, more complicated attempt at keeping `OCC.mdb` as a second file forever (a `CopyAppFiles` `includeMdb` flag + a startup self-heal copy) — `OCC.mdb` never had any sync of its own the way `ICAO_storedNotams.mdb` does, which is what caused a fresh local install to crash on startup missing it entirely (`LoadStationsCache`, `MainForm.Stations.cs`, `"Could not find file ...\OCC.mdb"`); merging the two files outright removed that whole class of problem instead of patching around the gap.
- **Startup crash logging** (`Program.cs`): `new MainForm()` is constructed as a plain statement (not inline inside `Application.Run(...)`) and wrapped in its own `try/catch` — a constructor-time exception previously unwound straight out of `Main()` with no dialog and no log, since it happens before `Application.Run`'s own message-loop exception handling (`Application.ThreadException`) even exists yet; exactly the "icon flashes then disappears" shape reported in practice. Any exception now writes to `crash_log.txt` next to the exe and shows a `MessageBox` pointing at it; `Application.ThreadException`/`AppDomain.CurrentDomain.UnhandledException` cover anything escaping later, during the message loop.
- **User identity**: `GetCurrentUserEmail()` — late-bound Outlook COM (`Session.CurrentUser.AddressEntry`), preferring `GetExchangeUser().PrimarySmtpAddress` over the plain `.Address` since on an Exchange account the latter is often an X.500 legacyExchangeDN string, not a real email. `EnsureUsersTable()`/`UpsertCurrentUser()` maintain a `Users` table (`ICAO_storedNotams.mdb`, `Email`/`FirstSeen`/`LastSeen`) — same idempotent-`CREATE TABLE` idiom as `EnsureEmailTable()`.
- **Writer/Reader lock**: `dispatch_watch.lock` on V:, next to `ICAO_storedNotams.mdb` — a flat `Email|Token|Machine|AcquiredAtUtc|LastHeartbeatUtc` text file (same style as `MmScheduleCursor.txt`). `AcquireOrPromptForLock()` claims Writer outright if the lock is missing/ours/stale (`LastHeartbeatUtc` older than 90s = 3× the heartbeat interval); otherwise it shows a two-button dialog (`ShowLockPromptDialog`, "In use by {email}... Continue as Reader, or take over as Writer?"). A 30s `Timer` (`LockHeartbeatTick`) then does double duty for the rest of the session: as Writer, it refreshes `LastHeartbeatUtc` (keep-alive) and checks the lock's `Token` is still its own — if someone else claimed it (a forced takeover), it immediately does a best-effort `UploadDbToV()` (silent, non-`MessageBox` twin of `EndApp`'s upload step — the confirmed policy is "emergency-save whatever we have" before losing write access, since the previous Writer might have unsynced edits), flips to Reader, and shows a transient corner notification (`ShowTransientNotice`) naming who took over. As Reader, the tick is a no-op — becoming Writer again means relaunching, there's no live mid-session promotion. `ReleaseLock()` deletes the lock on graceful close, before `EndApp()`'s own upload, so the next launcher never sees a stale "in use" state.
- **Reader-mode enforcement**: `EnsureWriterOrWarn()` — a single guard (`if (!IsWriter) return false` + an explanatory `MessageBox`) called at the top of every DB-write-triggering entry point: `Btn_submitNotamsClick`/`Keep_Notam`/`Ignore_Notam`/`StationImpactSet`/`StationSupSet`/`StationSaveRemark` (`MainForm.NotamFilter.cs`, plus `Filter_Notams`'s own automatic auto-Keep/demote pre-pass, which runs on every render rather than in response to a click and so is gated by a plain `if (IsWriter)` around its write loop instead of the popup-showing guard), `RunDbUpdatePipeline` (`MainForm.NotamData.cs`), `RefreshFlightSchedule` (`MainForm.FlightSchedule.cs`), `Btn_sendReportsClick`/recipient add-remove (`MainForm.Email.cs`), APT List save/delete (`MainForm.AirportList.cs`), RWYs save/re-import/add (`MainForm.Rwys.cs`), Keywords add/remove (`MainForm.Keywords.cs`), the Admin tab's Save (`MainForm.Admin.cs`), and the AIP SUP Avio-checkbox bridge (`update_SUP_Avio`, `MainForm.AipSup.cs`). `ApplyReaderModeUi()` additionally disables the primary write-triggering buttons outright (called once at startup if opening as a Reader, and again if a live Writer gets forced down) so Reader mode reads as read-only at a glance, not just as a wall of blocked-action popups.
- **Inactivity auto-save**: `StartIdleAutoSave()` installs an `IMessageFilter` (`IdleActivityFilter`) watching `WM_MOUSEMOVE`/`WM_KEYDOWN`/`WM_LBUTTONDOWN` app-wide to track `_lastActivityUtc` — WinForms has no built-in idle-detection API, this is the standard technique. A 10s `Timer` checks elapsed idle time; past 2 minutes and only if `IsWriter`, it calls `UploadDbToV()`, refreshes the lock heartbeat, and shows the same transient corner notification as the forced-takeover case, then resets the idle clock so it doesn't refire every 10s for the rest of the idle stretch.

### Database Access Rules

- Provider: `Microsoft.JET.OLEDB.4.0` (32-bit, x86 target)
- OleDb uses **positional `?` placeholders** — never named `@param`
- Always `Parameters.AddWithValue("?", value)` for every `?` in the query, in order
- Use `ExecuteNonQuery()` for INSERT/UPDATE/DELETE; `ExecuteReader()` for SELECT
- Open connection, execute, close immediately — no connection pooling pattern

### Key Data Flow

1. **GetCSV** → downloads ICAO CSV → saved as `ICAO-CSV.csv`
2. **Split** → parses CSV, inserts rows into `storedNotams_table`
3. **NewNotams** / **DelOld** → syncs `storedNotams_table` → `filteredNotams_table`
4. **Filter_Notams** → dispatcher classifies each NOTAM (Keep/Ignore, Impact type, Remark)
5. **Report** / **Sup_Report** → generates HTML → displayed in `WebBrowser` control → Print or PDF export

### DB Update pipeline (`Btn_updateDBClick` / `Btn_dbUpdateQuick` on the Filter tab)

- `RunDbUpdatePipeline(onCompleted)` runs `GetXML → deleteWithdrawnedNotams → NewNotams → DelOld` on a **`BackgroundWorker`** (not the UI thread), reporting weighted progress (download jumps to ~2%, then 30/45/90% boundaries for the three DB-diff phases) into a single dark, non-modal progress dialog (`ShowDbProgressForm`/`UpdateDbProgress`/`CloseDbProgressForm`) — replacing the old sequence of blocking popups + a final `MessageBox`. `Btn_dbUpdateQuick` (top bar) and `Btn_updateDB` (DB Update tab) both call `RunDbUpdatePipeline`; the quick button's `onCompleted` refreshes the current Filter/Station view afterward.
- `NewNotams`/`deleteWithdrawnedNotams`/`DelOld` each take an optional `Action<int,string> onProgress` and open **one** OleDb connection for their whole body (previously `NewNotams` opened 2 + 2×N connections — one full-table scan with columns resolved by `GetOrdinal` name lookup, not hard-coded index, replaced the old per-key `SELECT * WHERE key=?` round trip). Diff/dedup logic uses an in-memory `HashSet<string>` of keys instead of one `SELECT COUNT(*)` query per row.
- Since these methods now run off the UI thread, writes to the debug textbox go through `SetLog()` (marshals via `Invoke` if needed) instead of `RchTxtCSV.Text = …` directly.
- `RefreshLastDbUpdateLabel` (top bar `Lbl_lastDbUpdate`) shows when the pipeline last **completed**, read from `last_db_update.txt` next to the exe (written by `SaveLastDbUpdateTimestamp`) — deliberately not the `.mdb` file's own last-write time, which also changes on V: drive sync (`StartApp`/`EndApp`) and would look "fresh" even if DB Update was never run.

### Flight Schedule tab + Admin tab

- `MainForm.FlightSchedule.cs` calls two web services (same fleet-ops "WebService-Archives" infrastructure the NOTAM download uses, but a separate flight-planning system): **`getFlightList`** (`FlightScheduleService.svc`, param `FLDT=ddMMMyy`) returns one day's flights — `Fltleg_ID`, `FPfx`/`FLNr` (Callsign), `ACREG` (Reg), `STD`, `CrewMembers` (Crew), and `departureAerodrome`/`arrivalAerodrome` (nested `{iataID, icaoID}` elements — `NestedIata` reads the Origin/Dest IATA code out of each) all come from here, in the `http://www.fwz.aero/Schemas/StandardInterfaces` XML namespace (`XDocument`/`XNamespace`, not the NOTAM tab's regex-splitting style, since this feed is a flat non-legacy schema). **`getBriefing`** (`BriefingService.svc`, param `FLTLEG_ID`) is the same per-flight briefing endpoint the fleet's separate archive/reader app also uses to fetch OFP/MET/NOTAM PDFs.
- **`FetchBriefingDetails`** (formerly `FetchSta`) parses more out of that same already-downloaded `getBriefing` XML rather than just regexing `<ScheduledTimeOfArrival>` (STA) — no new network calls. The document wraps two XML namespaces (the outer `StandardInterfaces` envelope and an inner ARINC 633 payload at `http://aeec.aviation-ia.net/633` where the flight-plan detail actually lives), so every lookup matches on **local name only** (`.Descendants().Where(e => e.Name.LocalName == "...")`), never a fully-qualified `XName` — a namespace-qualified lookup silently finds nothing. It extracts: main-leg flight time (`FlightPlanSummary/FlightTime/EstimatedTime/Value`, ISO-8601 duration e.g. `PT4H16M00.000S`, converted once to integer minutes by `ParseIsoDurationMinutes`), and up to two destination alternates from `<AlternateFuel>` elements — each one's direct-child `<Airport airportFunction="...">` (`PrimaryArrivalAlternateAirport`/`ArrivalAlternateAirport` = a destination alternate; `DepartureAlternateAirport`/`ETOPSAdequateAirport` ignored) gives the ICAO (`AirportICAOCode`), and the `AlternateFuel`'s own **direct-child** `<Duration><Value>` gives the flight time *to* that alternate — critically distinct from the nested `<FinalReserve><Duration>` sibling (a fixed reserve-fuel duration, not a flight time); mixing the two up silently produces a bogus alternate flight time. Alternates are de-duplicated by ICAO (`seenAlt`); the first distinct one found becomes Alt1, the second Alt2. All of this only exists once a flight plan has actually been built — same as STA today — so `Alt1`/`Alt2`/the duration fields are blank until then, and always blank for `Source='MM'`/`'CSV'` rows (neither has a real `Fltleg_ID` to brief).
- `FlightSchedule` table gained `Alt1 TEXT(4)`, `Alt2 TEXT(4)`, `FlightTimeMin LONG`, `Alt1TimeMin LONG`, `Alt2TimeMin LONG` (idempotent `ALTER TABLE`, `EnsureFlightScheduleTable`).
- `RefreshFlightSchedule()` walks `FLDT` = today .. today+7 (the feed's actual retention past 7 days is unconfirmed), then calls `getBriefing` **once per flight** to backfill STA + the fields above — this is the expensive part (a few hundred calls across a week), so it's cached in the `FlightSchedule` table keyed by `FltlegID` and only re-fetched when a flight's `STD` has changed since the last cached value (the cache dictionary carries the full `BriefingDetails`, not just STA, so a cache hit skips `getBriefing` entirely). Runs on a `BackgroundWorker` with the same dark progress-dialog styling as DB Update (`ShowFsProgressForm`/`UpdateFsProgress`/`CloseFsProgressForm`).
- **Conflicted rows are highlighted, live grid and export alike**: `LoadFlightScheduleGrid` calls `GetConflictedFltlegIds()` (`MainForm.Conflict.cs`) — every `FltlegID` with at least one active Conflict-tab match, automatic or manually-forced — and tints those rows' `DefaultCellStyle` (`BackColor`/`SelectionBackColor`, light red). `BuildFlightScheduleHtml` (Export PDF / Send Reports email attachment, below) uses the same set to add an inline `style="background:#ffcdd2"` to the matching `<tr>`, so the highlight survives into the exported/emailed version too, not just the live tab. `GetConflictedFltlegIds` and `BuildConflictReportHtml`'s per-NOTAM matching both funnel through the same `TryComputeConflictMatches` helper (factored out for this reuse), so a dismissed match or one outside the 7-day window is consistently excluded everywhere.
- Grid columns (all UTC, `Reg` shown raw/undashed): Date, Callsign, Origin, Dest, Reg, STD, STA, **Flight Time, Alt 1, Time to Alt 1, Alt 2, Time to Alt 2**, Crew, **Force Conflict** — sorted by `STD` ascending. The three duration columns are formatted `H:mm` (`FormatMinutesHhmm`, blank when the underlying minutes value is ≤0) rather than shown as raw minutes. A hidden `FltlegID` column (not part of the per-column filter row, which is strictly 1:1 with the visible/filterable columns) backs the **Force Conflict** button column — see the Conflict tab's manually-forced-conflict writeup above for what it does. Loads on `TabPage.Enter` plus a manual Refresh button (unlike the Report tabs, a full refresh here means dozens–hundreds of network calls, so an explicit re-trigger is worth keeping). The separate `BuildFlightScheduleHtml` query (Export PDF) was deliberately left unchanged — Alt1/Alt2/flight-time are a grid-only addition, out of scope for that export.
- **Throttled automatic refresh**: a full `RefreshFlightSchedule()` used to re-run on *every* `FlightScheduleTabEnter`, even if the data was seconds old. `TryAutoRefreshFlightSchedule()` (`MainForm.FlightSchedule.cs`) is now the shared gate for every automatic trigger — completing NOTAM triage (`Filter_Notams()`'s "ALL NOTAMS CHECKED" branch, `MainForm.NotamFilter.cs`), opening the Flight Schedule tab, and opening the Conflict tab (`ConflictTabEnter`, `MainForm.Conflict.cs`, which never refreshed this table at all before) — silently skipping (no `EnsureWriterOrWarn` popup) when not Writer, a fetch is already running, or the last *successful* refresh (`_lastFsRefreshCompletedUtc`, set in `RefreshFlightSchedule()`'s `RunWorkerCompleted`, manual clicks included) was less than 5 minutes ago. `FlightScheduleTabEnter` now also calls `LoadFlightScheduleGrid()` unconditionally (cheap, local-only) so the grid still reflects current DB contents even on a throttled visit where no network refresh runs. The manual **Refresh** button bypasses the throttle entirely, as before — and since it goes through the same completion path, it resets the 5-minute clock for every other trigger too.
- **Auto-saves its own PDF on every refresh completion** (manual or automatic): `RunWorkerCompleted`'s success path now also calls `ExportToPdf(BuildFlightScheduleHtml(), "Flight_Schedule", true)` right after `LoadFlightScheduleGrid()`, updating the same progress dialog's status line (`UpdateFsProgress(100, "Saving Flight Schedule PDF...")`) instead of popping a second confirmation. `ExportToPdf` (`MainForm.Export.cs`) gained a `silent` parameter (default `false`, unchanged for the existing manual "Export PDF" buttons) that suppresses its own success/failure `MessageBox` and returns a `bool` instead; the auto-export is wrapped in `try/catch` so a PDF failure (missing `wkhtmltopdf.exe`, V: unreachable) can't break the refresh completion itself.
- **Export PDF** (`BuildFlightScheduleHtml`, top bar): unlike the tab's own 14-day grid, this renders only the next 7 days (`[nowUtc, nowUtc.AddDays(7)]`), grouped by calendar date with a colored date-header row per day (same visual language as `Section()`'s headers on the NOTAM Report tab) — reuses the same `FlightSchedule` query as `LoadFlightScheduleGrid`. Writes `{yyMMdd}-Flight_Schedule.pdf` into `ReportsDir`, the third attachment on the Send Reports email (`MainForm.Email.cs`). Since there's no `WebBrowser` control on this tab, `ExportToPdf` gained a `(string html, string baseName)` overload (`MainForm.Export.cs`) — the original `(WebBrowser, string)` version is now a one-line wrapper around it — so this export doesn't need an offscreen/hidden browser control just to hold `DocumentText`.
- **Admin tab** (`MainForm.Admin.cs`) holds the two editable base URLs (`_flightScheduleBaseUrl`, `_briefingBaseUrl`), the **callsign prefix filter** (`_callsignPrefixFilters`, default `TAY,FDX,DHL`), and the **Movement Manager messages folder** (`_mmMessagesPath`, see below) — all persisted to `ArchiveConfig.xml` next to the exe (created with the current defaults — `10.48.12.43:5458`/`5455` — on first run). This is scoped to the Flight Schedule feature only: the NOTAM tab's own `getAdHocNOTAM` call in `MainForm.NotamData.cs` stays hardcoded and is untouched. `CallsignAllowed(callsign)` (a prefix `StartsWith` check, empty list = no filtering) is applied at every ingestion point in `FetchFlightSchedule` (webservice, MM, CSV) and in a cleanup pass that deletes any already-stored row (any source) that no longer matches — needed because editing the filter on the Admin tab doesn't retroactively touch rows fetched under a looser/different filter.
- **Movement Manager XML feed** (`MainForm.MmSchedule.cs`, `LoadMmSupplementalFlights`) — the **highest-priority source after the webservice** for the 7-day window (ahead of the CSV fallback), reading `flightInfo_V2` XML messages ASL's Movement Manager exports continuously into per-day (`yyyyMMdd/`) folders under `_mmMessagesPath` (a network share by default). Same XML namespace/schema family as `getFlightList`. Most files carry a single `<flight>`, but a **twice-daily ACCLAIM batch file** (~05:30/16:00, ~150-200KB) carries up to ~200 sibling `<flight>` elements spanning several days each — this batch is the only real source of visibility beyond day+2, since the small per-flight delta messages are mostly near-term changes; an earlier version used `Element()` (first child only) and silently dropped ~99% of each batch file's content, capping the grid at day+2 — fixed by walking all of them via `Elements()`.
  - Keyed by `carrierCode|flightNumber|originDate`; the *latest* message per key (by file `LastWriteTimeUtc`) wins, and a final `action="C"` on a key means the flight is cancelled and excluded.
  - **The callsign is always rebuilt from `carrierCode`+`flightNumber`, never taken from the message's own `<callsign>` tag** — confirmed by cross-checking a live duplicate pair against the source XML that `<callsign>` sometimes holds the *tactical/rotation* callsign (e.g. `"TAY6BS"`) rather than the flight-number-based one the webservice uses for the exact same leg (e.g. `"TAY4337"`), even in the fuller ACCLAIM batch files — the same failure mode the CSV's `ATC` field once had. `_mmCarrierPrefixMap` (`3V→TAY, QY→BCS, 5O→FPO, 5H→ABR, FX→FDX`, small/extensible) maps the 2-letter IATA `carrierCode` (ambiguous — shared by several different operators) to the operator prefix; `prefix + flightNumber` is the final callsign. A carrier not in the map is skipped outright (not enough information to attribute it).
  - `Source='MM'` rows use a synthetic negative `FltlegID` (`MmSyntheticId`, a hash of the identity key) kept in a **different negative sub-range than the CSV fallback's `-csvId`** so the two synthetic ID spaces can never collide. `scheduledDepartureTime`/`scheduledArrivalTime` map straight to STD/STA — no `getBriefing` call needed, unlike webservice-sourced rows.
  - **Resumable read**: `MmScheduleCursor.txt` (shared on V:, `VAppFolder` — not `Application.StartupPath`-relative, since `RefreshFlightSchedule` only ever runs as Writer so there's no write-contention risk, and sharing it means whichever dispatcher is Writer today resumes from wherever the *previous* Writer left off instead of a cold per-machine cursor forcing a full backlog re-scan; `"yyyyMMdd|ISO-timestamp"`) records the last folder date + file write-time actually processed, so each refresh only reads files newer than the cursor instead of reprocessing the backlog; a fresh install with no cursor starts from *today − 2 days* rather than the full history.
  - **Folder listing avoids the whole share's history**: day-folder candidates are probed directly (`Path.Combine(_mmMessagesPath, d.ToString("yyyyMMdd"))` + `Directory.Exists`, for `d` from `cursor.FolderDate` to today) instead of `Directory.GetDirectories(_mmMessagesPath)` + client-side date filtering — the latter lists the share's *entire* archived history over the network just to filter it down to the last few days, which dominated real 4+ minute stalls.
  - **Parallel file reads**: within a day-folder's catch-up set, each file's `XDocument.Load` (an independent UNC round-trip) runs concurrently (`Parallel.For`, `MaxDegreeOfParallelism = 8`) since network latency — not parsing — is the actual cost. The parsed `<flight>` elements are only collected per file during the parallel pass; applying them to the shared `byKey` dictionary happens in a second, strictly sequential pass afterward, in file-write-time order, so "the latest message per key wins" (above) stays deterministic regardless of which parallel read finishes first.
- **`MergeKey(callsign, origin, dest, fldt)`** (`MainForm.FlightSchedule.cs`) — the flight-leg identity shared across webservice/MM/CSV, used both to skip a lower-priority source already covered by a higher one and to detect a placeholder that's since "graduated". Deliberately **not** keyed by exact STD: the same callsign can fly two different legs the same day (e.g. `CDG-HEL` then `HEL-TLL`), so `Origin`/`Dest` keeps those distinct, but a schedule revision of only a few minutes between two updates for the *same* leg must not read as a different flight. An earlier STD-exact key caused exactly that — a stale MM/CSV placeholder never graduated because its STD differed by ~10min from the webservice's later, revised STD for the same leg, leaving both rows behind as apparent duplicates.
- **`NormalizeIata`/`_iataAliasMap`** (`MainForm.FlightSchedule.cs`): some stations are the same physical airport under two different IATA codes (e.g. EuroAirport Basel-Mulhouse-Freiburg: `BSL` vs `MLH`) — different sources/messages report one or the other for what's otherwise an identical leg, reading as a duplicate. Applied to `Origin`/`Dest` at all three ingestion points (webservice, MM, CSV) before the merge key is built, normalizing to a single canonical code (`BSL→MLH`). Existing rows self-heal on the next refresh since they're matched and `UPDATE`d by the same `FltlegID` regardless of the previously-stored (un-normalized) value.
- **Stale-row cleanup** in `FetchFlightSchedule`: FPM sometimes reissues a new `Fltleg_ID` for a flight that already has a row from an earlier refresh (a crew update or a schedule shift of a few minutes), leaving the old ID's row behind forever — different key, so it's never updated in place, and nothing previously deleted it, producing duplicate-looking rows for the same physical flight. Any `Source='WS'` row (or legacy blank-`Source` row, treated the same) whose `FltlegID` isn't in `wsIdsSeen` (the set the webservice actually returned across this run's day+0..+7 window) is dropped in the same cleanup pass as the CSV/MM/routeless/callsign-filter purges; `Source='MM'` rows get the equivalent check against `mmIdsSeen`. Separately, **any row (any source) whose `STD` is already in the past** is purged every refresh. Finally, a **general duplicate pass** groups all remaining rows by `MergeKey` regardless of source and keeps only the single best-scored one (non-blank `Crew` > `Source` priority WS>MM>CSV > non-blank `STA`) — a safety net catching duplicates left over from before `MergeKey` was fixed, or from any other source-specific bug, rather than relying solely on each source's own graduation logic.
- `BuildFlightScheduleGrid` uses a **`Dock`-based layout** (fixed-height `Panel` `Dock=Top` for the title/Refresh button, `_fsDgv` `Dock=Fill` added after it), unlike every other dynamically-built tab in this app (Filter/Station/APT List/RWYs all use hard-coded `Top`/`Size`). A fixed-size grid on this tab clipped rows past the tab's visible height — including the grid's own vertical scrollbar — with no way to reach them regardless of window size; `Dock=Fill` makes the grid always occupy the full remaining client area and scroll internally. Per-flight persistence in `FetchFlightSchedule` is wrapped in a `try/catch` so one bad row can't silently truncate the rest of the week; a flight whose `getBriefing` 404s (briefing not generated yet, common for far-future legs) is still persisted with a blank STA rather than being dropped from the list.
- **CSV fallback, last resort** (`LoadCsvSupplementalFlights`): FPM only publishes a flight to `getFlightList` once its plan is calculated, so upcoming flights can be temporarily invisible; the MM XML feed (above) now covers most of that gap, so the CSV is only consulted for whatever neither the webservice nor MM already cover (`wsKeys`/`mmKeys` are both checked before adding a CSV row). As a workaround a dispatcher drops the FPM "Refuel EU" CSV export into `_flightSchedCsvPath` (`MainForm.Admin.cs`, Admin-tab editable, shared on V: by default — not `Application.StartupPath`-relative, since each dispatcher now runs their own local install and a CSV dropped into a local folder would only ever be visible to that one instance) — filename doesn't matter, `FindLatestFlightSchedCsv` picks the most recently modified `*.csv` there. `ParseCsvFile` reads it keyed by header name (`ID`, `ATC`/`Flight` → Callsign, `Aircraft` → Reg, `STD`/`STA`, `DEP`/`ARR` → Origin/Dest), since the export's column order/count isn't a contract this app controls. CSV rows are stored in the same `FlightSchedule` table with `Source='CSV'` and a synthetic `FltlegID` = the CSV's own numeric `ID` column **negated** (real `Fltleg_ID`s from the webservice are always positive, so this can never collide, and re-running against the same CSV updates the row in place rather than duplicating it). The CSV has no crew column, so `Crew` is left blank for these rows; `STA` is taken directly from the CSV (already computed by FPM) rather than via `getBriefing`, since a CSV-only flight has no real `Fltleg_ID` to brief. **Merge/graduation**: `MergeKey` (`Callsign|STD`) is the identity used to detect a CSV placeholder that now has a matching webservice row — once that happens the CSV row is deleted so the webservice version (now authoritative) is the only one left; CSV rows no longer present in the latest export are dropped the same way. The CSV's `STD`/`STA` (`dd/MM/yyyy HH:mm`) are **assumed UTC** to match the webservice's convention — not confirmed by the export itself, worth checking against a known flight if merged times look off by a few hours.
- **`BuildCsvCallsign`**: the CSV's own `ATC` column is a *tactical/rotation* callsign (e.g. `"TAY7LL"`) shared by several different legs of the same rotation, not the flight number — using it as-is produced duplicate-looking rows. The real flight number lives in the separate `Flight` column instead (e.g. `"3V4267"`, prefixed by a marketing/codeshare code that itself can start with a digit, like `"3V"`), so the callsign is rebuilt as ATC's leading letters (operator code, e.g. `"TAY"`) + the **last** run of digits in `Flight` (e.g. `"4267"`) → `"TAY4267"`. Taking the *first* digit run instead of the last was an earlier bug on this specific helper (grabbing the stray `"3"` from `"3V4267"`'s codeshare prefix) — fixed, but turned out to be a red herring for the actual recurring `"TAY3"` reports (see below).
- **Routeless placeholder flights ("TAY3" bug)**: `getFlightList` also returns technical/placeholder `<Flight>` entries alongside real ones — same `STD`/`ACREG` as a genuine flight, but `FLNr` defaulting to `"3"` and no `departureAerodrome`/`arrivalAerodrome`/`CrewMembers` at all. Confirmed by cross-checking a live "TAY3" row against the FPM CSV export: no matching duplicate row existed there, so the CSV parser wasn't the source. Both `FetchFlightSchedule`'s webservice loop and `LoadCsvSupplementalFlights` now skip any parsed flight where `Origin` and `Dest` are **both** blank (a real flight always has a route); the cleanup pass also purges any such routeless row already sitting in the table from before this guard existed.

- **Conflict definition**: a NOTAM at station X conflicts with a `FlightSchedule` flight when X is the flight's `Origin` and the NOTAM's `[startdate, enddate]` **overlaps** `[STD-w, STD+w]`, or X is the `Dest` and it overlaps `[STA-w, STA+w]` (`Overlaps` — simple interval-overlap test, not "NOTAM must span the whole window"), where `w` = `_conflictWindowHours` (Admin tab, `MainForm.Admin.cs`, default 12, persisted in `ArchiveConfig.xml` as `ConflictWindowHours`). `LoadFsFlights()` reads the same `FlightSchedule` table the Flight Schedule tab already populates. `ConflictTabEnter` does kick a throttled background refresh of it (`TryAutoRefreshFlightSchedule`, see the Flight Schedule tab's own write-up above) but doesn't wait on it — this render pass always builds from whatever's already stored; if that table is empty, `Build_Conflict_Report()` prepends a warning banner telling the dispatcher to load Flight Schedule first, rather than silently rendering an all-empty report.
- **Day+7 cap**: the whole tab is capped to `[nowUtc, nowUtc.AddDays(7)]` regardless of how far ahead `FlightSchedule` itself reaches (it can extend well past 7 days via the CSV fallback) — for A/N/C/F this means a candidate flight match is only counted if its `STD`/`STA` falls at or before that cutoff (in addition to the existing `Overlaps` check); for D it's the NOTAM's own validity window against that same cutoff (see below).
- **"Not ALTN" (D) is flight-independent, but a real diversion-time conflict is highlighted**: unlike every other impact code, D doesn't need a matching flight at all — whether a station can be used as an alternate isn't a function of which flights happen to touch it as origin/destination. `Build_Conflict_Report` shows every Kept, D-classified NOTAM whose `[startdate, enddate]` overlaps `[nowUtc, nowUtc.AddDays(7)]` — no `GetIATA`/flight-loop step runs for this impact code (a D NOTAM at a station with no IATA mapping still shows; the IATA lookup only exists to match flights for A/N/C/F). In addition, the D branch checks every flight where this station (ICAO — `FlightSchedule.Alt1`/`Alt2` are stored as ICAO, unlike `Origin`/`Dest` which are IATA, so no IATA conversion needed here) is the filed **Alt1 or Alt2** (`MainForm.FlightSchedule.cs`, see below): estimated arrival at the alternate = `f.Std + FlightTimeMin + Alt1TimeMin` (or `Alt2TimeMin`), tested via `OverlapsSchedule` against the NOTAM's window using a **second, independent** window — `_altnConflictWindowHours` (Admin tab, `MainForm.Admin.cs`, default 2, persisted as `AltnConflictWindowHours`) — rather than `_conflictWindowHours`. A card with at least one such match is sorted to the top of the D section (`cardsByImpact[impact].Insert(0, ...)` instead of `.Add(...)`) and rendered with a red-highlighted style (`.cardAlert`/`.flightChipAlert`, `BuildConflictCardHtml`'s new `highlight` param) — a real time-specific diversion conflict reads as materially more urgent than the section's default "not usable as an alternate at all, regardless of any flight" listing.
- **Recurring D)-item schedules** (`ParseNotamActiveWindows`/`OverlapsSchedule`): matching a flight against a NOTAM's raw `[startdate, enddate]` validity window overcounts conflicts for NOTAMs only active part of the time within that window (e.g. `"MON 0500-2359, TUE 0000-0100"` closures inside a months-long validity period) — a flight on any other day of the week was still flagged as conflicting. `ParseNotamActiveWindows` tries several recognizable schedule shapes, in order, and uses whichever is found first: a day-of-week list (`_dayItemRe`, `\b(MON|TUE|...)\b(?:-\b(MON|...)\b)?\s+HHMM-HHMM`, comma-separated entries, `MON-FRI`-style same-week ranges), a **day-of-month / month+day(-range) list** (`_monthDayItemRe`, e.g. `"11 2330-0245, 13 0001-0245"` or `"AUG 11-13 0530-1600"` — a very common NOTAM shape the day-of-week regex can't match at all, since it requires letter tokens where this one requires a leading digit, so the two can never collide), a `DAILY HHMM-HHMM` pattern (`_dailyRe`), or — as the last resort, only tried once none of the above match — a **bare `HHMM-HHMM` with no day/date qualifier at all** (`_bareTimeRangeRe`, e.g. a D)-item that's just `"2130-0100 RWY 04 ILS ... U/S DUE TO MAINT"`): standard NOTAM convention reads an unqualified time range as implicitly daily, same meaning as an explicit `DAILY` prefix — without this, such a NOTAM fell all the way back to the whole-validity-window check and over-matched flights at any time of day. `ScheduleEntry.Kind` (Weekly/MonthDay/Daily) and `EntryMatchesDate` unify the per-day occurrence expansion across all shapes (one occurrence per matching calendar day across the NOTAM's validity, clipped to it, handling overnight ranges like `2230-0330` by rolling the end into the next day; a `MonthDay` entry with no month prefix matches that day-of-month in any month). `OverlapsSchedule` (used by both the A/N/C/F/M flight-matching branch and the D/Not-ALTN alternate-diversion check, since both funnel through the same parser) checks the flight time against each occurrence instead of the whole window. **If no recognizable schedule is found, it falls back to the original whole-window `Overlaps` check** — an exotic/unparsed D) item never silently hides a real conflict, it just doesn't get the narrower treatment. `FRI-MON`-style wraparound day/date ranges aren't supported (skipped, same safe fallback) in any of these shapes.
- **`StripLeadingNoMarker`**: `GetXML`/`Split` (`MainForm.NotamData.cs`) prepends a literal `"No"` line to the `all` text field whenever a NOTAM's D) (schedule) field is absent — the same marker `NotamRemarkDefault` (`MainForm.NotamFilter.cs`) already checks for to fall back to the validity period instead of using it as a remark. `BuildConflictCardHtml`/`BuildNotAltnRowHtml` strip that leading `"No"` line before displaying the NOTAM's full text (it reads as a parsing glitch, not as data) — but only for display: the schedule-regex matching above (`OverlapsSchedule`) still reads the raw, unstripped `all` text, since the marker sits on its own line and doesn't interfere with matching.
- **Per-flight dismiss / manually-forced conflicts**: two workflow escape hatches on top of the automatic matching above, both live-tab-only (`rasterDiagrams=false` — the email/PDF render, `rasterDiagrams=true`, stays plain, non-interactive text, since there's no JS bridge there). **Dismiss** (false positive): every flight chip on the live Conflict tab renders as a native `<input type="checkbox" checked>` (safe here, unlike the AIP SUP tab's div-based checkboxes which exist specifically to work around `wkhtmltopdf`'s poor native-checkbox rendering — this is the live `WebBrowser` control only, never exported) whose `onclick` calls `window.external.DismissMatch(notamKey, fltlegId)` via a new `ConflictScriptBridge` (`[ComVisible(true)]`, same `ObjectForScripting` idiom as `AviobookScriptBridge`/`ReportScriptBridge`, wired onto `Web_Conflict` in `Build_Conflict_Report()`). `DismissConflictMatch` gates on `EnsureWriterOrWarn()`, inserts a `ConflictDismissals` row (`NotamKey`+`FltlegID`) on success, and **always** re-renders the tab afterward — the same re-render is what makes a blocked Reader's checkbox visually snap back to ticked, since the dismissal never persisted. `BuildConflictReportHtml` loads the dismissed set once (`NotamKey|FltlegID` keys) and skips adding any automatic match already in it, so a dismissed match simply never reappears. **Force** (false negative): the Flight Schedule tab (`MainForm.FlightSchedule.cs`) gained a hidden `FltlegID` column and a `"Force Conflict"` `DataGridViewButtonColumn` (same `CellContentClick`-dispatch pattern as the APT List tab's "Del" button) — its per-row text shows the currently-assigned NOTAM key or `"+ Force"`. Clicking opens `ShowForceConflictDialog` (same hand-positioned dark-`Form` pattern as `ShowLockPromptDialog`, `MainForm.Deployment.cs`): type an ICAO, search Kept/impact-classified NOTAMs there (`FindKeptNotamsForIcao`, same query shape as `BuildAirportHeaderHtml`/`ICAO_Notams`), pick one, Assign (writes a `ManualConflicts` row, `FltlegID`→`NotamKey`, replacing any prior one for that flight) or Clear. No impact/section picker — a forced conflict lands under whatever section the NOTAM's own `Impact` column already says, same as an automatic match. `BuildConflictReportHtml` folds in every `ManualConflicts` row for the NOTAM being rendered as an amber (`.flightChipManual`) `ConflictMatch` (`Manual=true`), regardless of impact code or whether the automatic matching found anything — this is what lets a forced conflict surface a card the automatic Origin/Dest/Alt matching alone never would have (the `if (matches.Count == 0) continue;` guard for non-`D` impacts now also keeps a NOTAM with only manual matches), and (like an automatic Alt1/Alt2 diversion match) sorts the card to the top of its section with the highlighted style. Its checkbox calls `RemoveManualConflict` instead of `DismissMatch` — deleting the `ManualConflicts` row outright rather than layering a dismissal on top, since it's the dispatcher's own record, not an auto-detected one to suppress.
- **ICAO vs IATA mismatch**: `filteredNotams_table.location` is ICAO (e.g. `EETN`), but `FlightSchedule.Origin`/`Dest` are IATA (webservice's `iataID`, and the CSV's `DEP`/`ARR` columns) — e.g. `TLL`, not `EETN`. Comparing them directly never matched anything, so `Build_Conflict_Report` converts the NOTAM's station via `GetIATA(location)` before comparing against `Origin`/`Dest`; a NOTAM at a station with no IATA mapping in `Stations_ICAO_IATA` is skipped (nothing to match flights against).
- **Full validity period next to the key**: the RMK line shown above the key is just the NOTAM's own first text line — for a recurring D)-item ("EVERY WED 0700-1000", "DAILY 2300-0459") that's only the weekly/daily pattern, not the NOTAM's actual overall `[startdate, enddate]`, so there was no way to see when it starts/ends without opening the full text. `BuildConflictReportHtml` now always formats `startdate`/`enddate` via the existing `FormatDate` (`MainForm.NotamFilter.cs`, the same `"dd MMM yyyy HH:mmz"` formatter `NotamRemarkDefault` already uses for this exact shape elsewhere) and passes it into `BuildConflictCardHtml` as `period`, rendered as a `.notamperiod` span next to the key — unconditionally, regardless of what the RMK line above already says.
- **Card rendering** (`BuildConflictCardHtml`): a leaner, fragment-only twin of `BuildAirportCardHtml` (which returns a *whole standalone document* sized for the Filter tab's own `WebBrowser` control) — reuses the same `LoadRwyGeo`/`BuildRwySvgGeo`/`BuildRwySvg`/`GetIATA`/`GetAirportName` pieces, but returns a `<div class="card">` meant to be concatenated with others into one page, since all conflicts across all sections share the single `Web_Conflict` document. Each card shows the airport (ICAO/IATA/name/RWY table/diagram), the matching flight(s) as chips (`ConflictMatch`: callsign, origin/dest role, STD/STA or diversion-arrival estimate, plus an interactive dismiss/remove checkbox on the live tab — see above), the NOTAM's remark, its key/reference, and its full text. The airport-header portion (ICAO/IATA/name/RWY table/diagram, the `.ahead` div) is factored out into its own `public string BuildAirportHeaderHtml(string AP, bool rasterDiagram, bool cidImages, Dictionary<string,string> inlineImages)`, reused both here and by the NOTAM Report tab's per-airport detail sections (`MainForm.Reports.cs`, below) so the RWY/geo-loading logic isn't duplicated.
- **`TryParseNotamDate`**: `startdate`/`enddate` are actually stored ISO-style with a `T` separator (built in `GetXML` as `"yyyy-MM-ddTHH:mm:ss.000Z"`) — an earlier version `ParseExact`'d against a space-separated format and silently failed on every row, so no NOTAM ever reached the overlap test regardless of window size. Fixed by extracting year/month/day/hour/minute positionally (same style as `dateTransformation`, which never assumed a particular separator at position 10). `FlightSchedule.STD`/`STA` are parsed as UTC (`DateTimeStyles.AdjustToUniversal|AssumeUniversal`) since they're stored `yyyy-MM-ddTHH:mm:ssZ`.
- Re-runs on **every** `TabPage.Enter` (not just the first visit), so switching back to Conflict after Kept-ing more NOTAMs or refreshing Flight Schedule always reflects current data. It also re-runs **without switching tabs**: `RefreshFlightSchedule()`'s completion handler (`MainForm.FlightSchedule.cs`) re-renders the Conflict tab if it's the currently active one when a refresh finishes — otherwise a refresh kicked off just from opening the Conflict tab (`TryAutoRefreshFlightSchedule`) would only show its fresh data the *next* time the tab was entered, since `Build_Conflict_Report()` itself only runs on `TabPage.Enter`. The Flight Schedule tab's own grid doesn't need the same treatment — `LoadFlightScheduleGrid()` already runs unconditionally in that same completion handler regardless of which tab triggered the refresh.

#### Auto-classification engine (Filter tab only)

- `SuggestImpacts(text, runways, keptUpper, extraIlsDownRwys)` returns an `ImpactSuggestion` (flags A/C/N/D/F + independent `Sup`, plus two auto-Keep-only signals `RwyClosure`/`IlsOutage` — see below). The rules were **derived and validated against the dispatcher's historical classifications** in `ICAO_storedNotams.mdb` (recall on the sample: D 7/7, N 2/2, F 3/3, A 22/30, C 3/6), then iteratively refined against real false positives/negatives found in production use. `keptUpper` is retained in the signature but no longer used (rules are per-NOTAM).
  - A restriction explicitly scoped to an **aircraft type this operator doesn't fly** (e.g. `"FOR A388 AND B748 ACFT : ... CANNOT BE CHOSEN AS AN ALTERNATE"`) short-circuits the whole function to an empty `ImpactSuggestion` right away — irrelevant regardless of which impact keywords also appear. The excluded-type list (`A388`, `B748`) is intentionally small/extensible.
  - **APT CLSD** fires on `AD CLSD`/`AERODROME CLOSED`, or when the NOTAM closes *every* runway of the airport (`ClosedThresholds` vs `ParseRunways` of the OCC RWY field) — a single runway closure with a parallel remaining is intentionally **not** flagged. `ClosedThresholds` requires the runway mention to carry an explicit `RWY`/`RUNWAY` keyword **and** `CLSD`/`CLOSED` to be the *nearest* status keyword to that specific mention within a ±20-character window (`IsClosedNearby`) — a bare digit pair anywhere in the text, a runway mentioned only as a location reference for an unrelated taxiway closure (e.g. "TWY R1 BTN RWY16R/34L AND TWY G"), or a *different, explicitly-OPEN* runway pair mentioned nearby in the same sentence as another pair's closure (e.g. "RWY 17L/35R CLSD DUE TO WIP RWY 17R/35L OPEN" — a plain "CLSD anywhere in the window" check let the first clause's CLSD leak into the second, OPEN pair's window) is **not** treated as a closure. "AVBL ONLY FOR TAXI(ING)"/"NOT AVBL FOR TKOF/LDG" phrasing is treated as an equivalent closure even without the literal word CLSD.
  - **No ILS** fires on the shared `IlsOutagePattern` constant (`ILS … U/S|UNSERVICEABLE|NOT AVBL|NOT AVAILABLE|NOT USABLE|ON TEST|ON (FLT|FLIGHT) CALIBRATION|DO NOT USE`), excluding: the `EXC LVP` case (that's CAT I, not No ILS); a DME-only outage (`DME … ASSOCIATED WITH ILS …` — a DME is a supporting component, losing it doesn't take the ILS itself out of service; the outcome-word alternation here mirrors `IlsOutagePattern`'s full set, not just `U/S|UNSERVICEABLE|NOT AVBL/AVAILABLE` — a real EDDC NOTAM phrased this as "ASSOCIATED WITH ILS RWY 22 ON MAINT. DO NOT USE", which the narrower list missed entirely, wrongly treating a DME-only outage as a real ILS outage); a **middle/outer marker-only outage** (`(MIDDLE|OUTER) MARKER … ILS`, same idea as the DME exclusion — a marker beacon is a supporting component, not the localizer/glideslope itself); and — like APT CLSD — suppressed if **another runway at the airport still has a working ILS** (`RwyInfo.CatMax >= 1`) not affected by this NOTAM. Whether that suppression **escalates to CAT I** instead of leaving the suggestion blank depends on how good that other runway's capability actually is: only escalate when the *best* surviving runway is exactly CAT I; a surviving CAT II/III runway suppresses to nothing at all rather than "C" — 5 independent dispatcher corrections (LEMD, LEST, PANC ×2, EPWA) rejected a "C" suggestion every time the other runway was actually CAT II/III, since a much better runway remaining elsewhere isn't a CAT-I-level event worth flagging. `extraIlsDownRwys` (built once per airport in `Filter_Notams` as `ilsDownUnion`, via `ExtractIlsDownRwys` — which also uses `IlsOutagePattern` — over every active NOTAM's text) folds in ILS outages reported by *other simultaneous* NOTAMs at the same airport, so e.g. two NOTAMs each reporting one end of the same runway's ILS "ON TEST" are recognised together as a full outage rather than each individually being suppressed by the other's (soon-to-be-down) runway.
  - **CAT I** also fires on a CAT II/III-not-available downgrade, matched in **either word order** — `"CAT II ... NOT AVAILABLE"` or the reversed `"NOT AVAILABLE: ... ILS CAT II"` (both seen in real NOTAMs; only the forward order matched originally).
  - **Not ALTN**: `\bPPR\b` excludes three false-positive shapes seen on NAVAID/TWY NOTAMs — a directly-following phone number ("PPR 617-561-1919", a ground-ops contact), a short duration ("AVBL PPR 10MIN", a prior-notice window for degraded equipment), or a VHF frequency ("PPR 131.1") — none of these are a real diversion/alternate restriction. An explicit **"EXCEPT ALTN"/"EXC ALTN"** carve-out (e.g. "RWY … NOT AVBL FOR LANDING, EXCEPT ALTN") suppresses the whole flag — the airport is still usable as a diversion despite the restriction. A bare "PPR ONLY" in an **airspace/opening-hours-activation context** (`OPR HR`/`OPERATING HOURS`/`ATZ|CTR|CTA ACTIVAT`, e.g. "CTA/CTR/ATZ ACTIVATED. AD/ATS OPR HR EXTENDED. PPR ONLY.") is also excluded — that's prior permission to enter/operate during the window, not a diversion-suitability restriction. **"NOT AVBL FOR LANDING" directly followed by "TRAFFIC"** (e.g. "MIDGU M717 NOT AVBL FOR LANDING TRAFFIC TO MUSCAT...") is also excluded — that's an en-route ATS-route/traffic-flow restriction on a point along an airway, not a statement that the destination airport itself can't be used as an alternate.
  - **SUP** requires an actual `SUP nnn/yyyy` reference (`Regex.IsMatch`, same shape as `ExtractSupRef`) rather than a bare `Contains("SUP")` — the naive substring check was a false positive on any word containing "SUP" (e.g. "SECONDARY POWER **SUP**PLY").
- `SuggestedSingleCode` collapses the suggestion to one Impact code by severity (A>N>C>D>F) because `Impact` stores a single code; it ignores `RwyClosure`/`IlsOutage` (those never select a chip by themselves). **SUP is fully independent** — stored in the dedicated `Sup` column (`Yes`/empty), with its reference (e.g. `SUP 056/2026`, via `ExtractSupRef`) in a separate `SupRef` column. `Sup`/`SupRef`/**`AutoKept`** columns are added by `EnsureSchema()` (idempotent `ALTER TABLE`), which **also migrates the legacy SUP model** (`Impact='AS'` with the reference in `Remark`) to the new one (`Sup='Yes'`, ref in `SupRef`, `Impact`/`Remark` cleared). No `Impact='AS'` rows should remain after startup; `"AS"` survives only as the SUP chip's colour code.
- **Auto-Keep / Auto-Un-Keep** (`Filter_Notams` only): a pre-pass promotes not-yet-kept NOTAMs to `Status='K'` (and sets `AutoKept='Y'`) when `SuggestImpacts` finds any impact, SUP, `RwyClosure`, or `IlsOutage` — the latter two exist purely so a runway closure or ILS outage always surfaces for review even when no selectable impact chip applies (e.g. one runway closed/ILS down but an alternate remains) — so the chips (or, for these two, nothing) render without the dispatcher having to click Keep by hand. The same pass **demotes** (`Status=''`, `AutoKept=''`) a NOTAM it previously auto-Kept if a classification-rule change means it no longer triggers any signal (e.g. an older, looser rule wrongly auto-Kept a plain TWY/DVOR/DME NOTAM). **`AutoKept` is the persistent (survives app restarts) marker distinguishing an engine promotion from a dispatcher's manual Keep** — every manual-Keep path (`Keep_Notam`, `StationImpactSet`, `StationSupSet`, `Ignore_Notam`) explicitly clears it, so a NOTAM the dispatcher actually touched is *never* silently reverted by this pass, even before an impact has been picked for it. `Ignore_Notam` also adds the ID to the session-only `_autoKeepSkip` set so an ignored NOTAM is not immediately auto-re-kept on the next render.
- **Impact checkboxes are "chips"** (`CreateChip`): a `Panel` with a left accent strip + borderless `CheckBox` (the checkbox's `Tag` holds its accent panel). `StyleChk(cb, code)` tints the chip in the impact colour when checked (`ImpactColor` → `Tint`), grey accent when not. Columns/widths are laid out strictly inside the passed control-box geometry (`ctrlLeft`/`ctrlW`).
- **Two independent remark textboxes** per NOTAM (`LayoutRemarkBoxes`): the impact remark and the SUP-reference box. Only the box(es) whose checkbox is selected are shown; one box → full width, two → 2⁄3 impact + 1⁄3 SUP. The impact remark default (`NotamRemarkDefault`) is the NOTAM's first line, or the validity period `start - end` when that line is just `No` — **except Fuel and MISC**, which default to the **entire NOTAM text** instead (a fuel restriction's actual detail is usually further down in the text than the first line). Applied in both flows: `FilterImpactToggled`/`AddFilterCheckboxes` (Filter tab) and `AddStationChips` (station view).
- **Visual-only until SUBMIT.** Nothing is written to the DB on click — `Btn_submitNotamsClick` reads the final state of `_pendImpactChks` / `_pendSupChk` / `_pendRemark` / `_pendSupRemark` and persists `Impact`, `Sup`, `Remark`, `SupRef` before marking `Checked='Y'`. **Ctrl+S triggers the same click** (`MainForm.cs`'s `ProcessCmdKey` override) whenever the NOTAM Filter tab is active and `Btn_submitNotams` is visible (i.e. the automatic Filter flow, not the manual ICAO station view, which has no Submit step to shortcut) — caught at the form level rather than via a control's own `KeyDown`, since the NOTAM cards/chips/textboxes this tab builds are all dynamic and there's no single control to hang a handler on.
- The **station view (`ICAO_Notams`)** is **fully auto-save, no SUBMIT/SAVE button**: impact/SUP chips write immediately (`AddStationChips` → `StationImpactSet` / `StationSupSet`, both set `Status='K'` when assigned; SUP also writes `SupRef`), and the remark / SUP-ref textfields save on `Leave` (`StationSaveRemark`). Changing an impact resets `Remark` so the new impact shows its own default. Impact chips are shown **only for Kept NOTAMs** (`if (kept)`); ignored/new ones show just a Keep button. `impactOn` excludes `"AS"`. (`tabPage2`/`Web_ICAONotams`/`ChckBox_SeeIgnored` still exist in the Designer but are orphaned — the tab is no longer added to `tabControl1`.)
#### Correction tracking (`MainForm.ImpactTracking.cs`)

- `LogImpactCorrection(icao, key, notamText, runways, suggestedImpact, finalImpact, suggestedSup, finalSup)` appends one CSV row to `ImpactCorrections.csv` (shared on V:, same folder as `ICAO_storedNotams.mdb` — deliberately **not** `Application.StartupPath`, since the multi-user deployment gives every dispatcher their own local install and a local-only log would only ever capture that one dispatcher's corrections) whenever a dispatcher's **final** classification for a NOTAM disagrees with what `SuggestImpacts`/`SuggestedSingleCode` suggested — accepted-as-is suggestions are not logged, keeping the file a signal of real classification errors to hand back for regex tuning. Columns: `Timestamp, ICAO, NotamKey, RunwayConfig, SuggestedImpact, FinalImpact, SuggestedSup, FinalSup, Action, NotamText`. `RunwayConfig` is formatted straight from the same `List<RwyInfo>` (`Desig`/`CatMax`) passed into `SuggestImpacts`, e.g. `"05:CAT1; 23:CAT3"` — exactly the config that drove the (possibly wrong) decision, so a case like "CAT I suggested despite another runway being CAT III" is visible directly in the row.
- Three write-paths feed it:
  - **Filter tab (pending model)**: the engine's suggestion for each NOTAM is snapshotted into `_pendSnapshot` (a `Dictionary<int, NotamSnapshot>`) at the same point `AddFilterCheckboxes` is called, since the pending chips/dictionaries only ever store `CheckBox`/`TextBox` references, not the original suggested code. `Btn_submitNotamsClick` compares each NOTAM's final submitted code/Sup against its snapshot and logs a correction if they differ. `_pendSnapshot` is cleared alongside the other `_pend*` dictionaries at the top of `Filter_Notams`.
  - **Station view (immediate-write model)**: `ICAO_Notams` now also parses `RWYs` into `runways` (previously only done in the Filter tab), threaded through `AddStationChips` → `StationImpactSet`/`StationSupSet`, which each recompute `SuggestImpacts` fresh and log if the toggle's resulting state disagrees — this is what catches "cleared a bogus Not ALTN suggestion" in the station view, not just the Filter tab.
  - **`Ignore_Notam`**: if the NOTAM being ignored has `AutoKept=='Y'` (it was only Kept because the engine auto-suggested a signal), its suggestion is recomputed and logged with `FinalImpact="(ignored)"` — captures the case where a bogus suggestion caused an unwanted auto-Keep that the dispatcher rejects outright rather than just clearing the chip.
- `CsvField()` is a small local CSV-quoting helper (wrap in `"…"`, double internal quotes, real newlines inside the quoted `NotamText` field) — no CSV writer existed elsewhere in the codebase to reuse. Logging is wrapped in `try/catch`; a failure here must never block the dispatcher's actual Keep/Impact workflow.

- **Top-bar layout** (`tabPage1`, all at y≈8): `Btn_filterNew` ("Filter New NOTAMS", green, x=7) → `Btn_dbUpdateQuick` ("DB Update", black, x=205, a quick-access duplicate of the DB Update tab's button) → `Lbl_lastDbUpdate` (gray "MAJ: …" timestamp, glued to `Btn_dbUpdateQuick.Right`) → `Lbl_ICAO` + `TxtBox_ICAO` + `Btn_ICAO` ("OK", blue-grey, x≈505+, left-aligned with the right NOTAM column, `Btn_ICAO` glued to `TxtBox_ICAO.Right`). The airport card (`Web_FilterHeader`) sits **below** the bar at `(7,44)`; the right column starts at `Top=48`.
- **`AlignTopBar()`** repositions all of the above with raw pixel values (matching the card column's hard-coded `Left=505`) at the very start of *every* `Filter_Notams`/`ICAO_Notams` render. This is necessary because these are Designer-time controls subject to WinForms DPI auto-scaling, while the dynamically-built NOTAM cards are placed with raw pixel math unaffected by auto-scale — without re-asserting their position every render, the two families drift apart on non-design-time DPI.
- **Scroll-position reset must happen *before* anything is (re)positioned**, as the very first statement of `Filter_Notams`/`ICAO_Notams` (`tabPage1.AutoScrollPosition = new Point(0, 0);`), not after. Positioning/adding controls to an `AutoScroll` panel while it's still scrolled bakes the current scroll offset into their effective location; resetting scroll afterward doesn't retroactively fix that. `TxtBox_ICAO` also responds to **Enter** (`TxtBox_ICAO_KeyDown` → `ICAO_Notams()`), and `Btn_filterNewClick` clears `TxtBox_ICAO.Text` when leaving the manual station view.
- **Keyword highlighting**: `_notamKeywords` are bolded/reddened (whole-word match only). `HighlightKeywords(rtb, startChar)` (RichTextBox) skips the first two lines (NOTAM ref + dates); `HighlightKeywordsHtml(text)` does the HTML equivalent for the mini WebBrowsers. The list is loaded from the `Keywords` table (`ICAO_storedNotams.mdb`, seeded with `_defaultKeywords` by `EnsureKeywordsTable()`) and editable via the **Keywords tab** — `_notamKeywords` is a runtime list, not a hardcoded constant.

### Runways data model (RWYs tab)

Per-runway data lives in a structured **`Runways`** table (`ICAO, QFU, Cat, DistM, Hdg, ThrLat, ThrLon, Ord`, created by `EnsureRunwaysTable()`). `Cat` (max approach type, e.g. `CAT 3`) is **manual** — the open-data CSVs do not include it; everything else is auto-filled from **`runways.csv`** (OurAirports data, copied next to the exe, scanned at runtime by ICAO). Adding an airport in APT List auto-imports its runways (`ImportRunwaysFromCsv` + `RegenerateRwyMemo`); existing airports migrate their legacy memo on first view (`MigrateLegacyMemo`, preserving the manual `Cat`, then `EnrichFromCsv`). The RWYs tab is a `DataGridView` editor (combo to pick the ICAO + Save / Re-import / Add RWY). **The legacy `Stations_ICAO_IATA.RWYs` memo is regenerated from the table** (`RegenerateRwyMemo`, lines `QFU: Cat DistMm`) so `ParseRunways` (ILS-downgrade context) keeps reading the memo unchanged.

**Airport diagram (`LoadRwyGeo` + `BuildRwySvgGeo`, `MainForm.NotamFilter.cs`)**: uses real threshold coordinates (equirectangular projection of `ThrLat`/`ThrLon`, true crossing angles and parallel spacing) when *at least one* threshold of the runway has coordinates (`HasGeo`/`HasCoords` — no longer all-or-nothing: a runway with a missing/zero threshold is skipped individually, projected from its other end's heading+length, rather than forcing the whole airport back to the schematic fallback `BuildRwySvg`, QFU×10 + length). `LoadRwyGeo` caches per-ICAO results in `_geoCache`, but **only once the result is non-empty** — an empty lookup (e.g. made before the CSV index below has finished loading) is left uncached so the next render retries instead of getting stuck on a stale empty result forever.

**CSV geo index (`MainForm.Rwys.cs`)**: `runways.csv` (~48k lines) is parsed once into an in-memory `_csvGeo` dictionary, loaded on a **background thread** (`PreloadCsvGeoAsync`, kicked off from the `MainForm` constructor) so the UI never blocks on it — `CsvGeoFor`/`EnsureCsvGeoLoaded` is thread-safe (lock + atomic dictionary swap) and returns empty (schematic fallback) if the render happens before the background load finishes. `ImportRunwaysFromCsv`/`MigrateLegacyMemo` (airport add, re-import, legacy migration) call `EnsureCsvGeoLoaded()` directly since those are occasional/one-off and can afford to block briefly.

### APT List tab (`DataGridView`, `MainForm.AirportList.cs`)

Rebuilt around a `DataGridView` (`_aptDgv`, same pattern as the RWYs tab's `_rwyDgv`) instead of hand-positioned dynamic controls:
- Columns: **ICAO** (bold), **IATA**, **Airport Name**, then checkbox columns **LH**/**FedEx**/**Charters** colour-coded to match the NOTAM/AIP SUP reports (RoyalBlue / purple `#663399` / SeaGreen — via `AptDgvCellPainting`, a `CellPainting` handler that custom-draws the checkbox glyph itself in the category colour while keeping the **cell background white**, not the reverse), and a **Del** button column.
- Checkbox columns commit **on click** (`CellContentClick` forces `_aptDgv.EndEdit()`) rather than waiting for focus to leave the cell, so toggling reads as instant — same feel as the AIP SUP report's checkboxes.
- **No Add/Edit form** — `AllowUserToAddRows` gives a perpetual blank row at the bottom; typing an ICAO into it triggers an INSERT (via `SaveAptRow`, fired from `CellValueChanged`) using `SELECT @@IDENTITY` to capture the new row's ID into `DataGridViewRow.Tag`, which every later edit/delete keys off. `_aptSuppressSave` guards programmatic `Rows.Add`/`Value` writes (e.g. during `LoadAptGrid` or auto-filling the name) from re-entering `SaveAptRow` through the same `CellValueChanged` event.
- **Airport name auto-fill**: `airports.csv` (OurAirports data, same file already shipped for runway geo) is parsed once into an ICAO → name index (`EnsureAirportNamesLoaded`, background-thread preload via `PreloadAirportNamesAsync`, quote-aware `CsvSplit` reused from `MainForm.Rwys.cs` since names can contain commas) — no network lookup. Existing rows with a blank `Name` are backfilled opportunistically every time the tab is loaded (`LoadAptGrid`); a brand-new row resolves its name synchronously (blocking `EnsureAirportNamesLoaded()` is fine here — an occasional one-off action, same precedent as the runway CSV import). The `Name` column on `Stations_ICAO_IATA` is added by `EnsureAirportNameColumn()` (idempotent `ALTER TABLE`, called from the constructor before `LoadStationsCache()`). `_stationsCache` (`MainForm.Stations.cs`) carries the name too (`GetOrdinal("Name")`, robust to column order) via the new `GetAirportName()` lookup, used by `BuildAirportCardHtml` to show the airport's full name as a line under "IATA: …" in the Filter tab's airport card.
- Search box (`_aptSearch`) filters ICAO/IATA live via `DataGridViewRow.Visible` (`FilterAptGrid`), client-side, no query re-run.
- `AptListTabEnter` (`APT_List.Enter`) reloads the grid every time the tab becomes active — not just once at startup — so names picked up by the background CSV index after the first visit (loading ~80k lines takes a few seconds) actually appear without the dispatcher having to edit a row to trigger a refresh.

### NOTAM Report / AIP SUP Report tabs — no button, auto-load on tab select

Both `Report()` (`MainForm.Reports.cs`) and `Sup_Report()` (`MainForm.AipSup.cs`) run automatically via `TabPage.Enter` (`TabPage4Enter` / `AipSupReportTabEnter`) — the reliable WinForms idiom for "this tab became active" (more so than `TabControl.SelectedIndexChanged`, which doesn't fire consistently in this app for tab-header clicks) — and re-run whenever the dispatcher changes the time-window radio (`RadBtn_reportWindowCheckedChanged` / `RadBtn_supReportWindowCheckedChanged`, wired to all four radios' `CheckedChanged`). There is no "Report !" button on either tab anymore. In `Section()`, sub-categories are listed AP Closed, RWY/TWY Closure, CAT I, No ILS, **Fuel, Not as Altn**, Misc — Fuel before Not as Altn, matching the Conflict tab's impact ordering.

**The live tab is summary-only; per-airport detail is generated on demand by Export PDF** (`Report()` vs `ExportNotamReportPdf()`/`BuildFullNotamReportHtml()`): building one detail section — airport header + rendered runway-diagram image + Kept NOTAMs — per **every station on the Airport List tab** made the tab itself painfully slow to open, since that used to happen on every `TabPage.Enter`/time-window change. `Report()` now only ever builds the summary table (`BuildSummaryHtml`, shared with the export path — the underlying NOTAM scan/impact tally is identical either way) and assigns it to `Web_report.DocumentText`; there are no per-airport sections in the live tab at all any more. `Btn_exportReportClick` calls `ExportNotamReportPdf()` instead of reading back `Web_report`'s content: it captures the current time-window radio state (`GetReportWindowBounds`, must run on the UI thread), then runs `BuildFullNotamReportHtml` — summary + one `BuildAirportDetailSectionsHtml` section per Airport List station, alphabetically by ICAO (`SELECT ICAO FROM Stations_ICAO_IATA ORDER BY ICAO`) — on a `BackgroundWorker` with a dark progress dialog (`ShowReportExportProgressForm`/`UpdateReportExportProgress`/`CloseReportExportProgressForm`, same styling as the DB Update/Flight Schedule dialogs), reporting "Building {ICAO} (i/n)..." per airport since the runway-diagram render + DB query is the actual slow part; `ExportToPdf` runs only once that full HTML is ready. Everything `BuildFullNotamReportHtml` touches (`BuildSummaryHtml`, `BuildAirportHeaderHtml`, OleDb, GDI+ diagram rendering) is plain data/string/file work with no `Control` access, so it's safe off the UI thread.
- **NOTAM key links behave differently live vs exported** (`AppendImpactRow`'s `interactiveLinks` param): since the live tab has no in-page detail section to jump to any more, its links (`interactiveLinks=true`) instead call back into the app via `window.external.OpenIcao(icao)` (`ReportScriptBridge`, `ObjectForScripting` set on `Web_report` — same COM-visible-bridge idiom as the AIP SUP tab's `AviobookScriptBridge`) → `OpenIcaoInFilterTab(icao)`, which switches `tabControl1` to the NOTAM Filter tab and drives its manual ICAO view (`TxtBox_ICAO.Text = icao; ICAO_Notams();`) to show that station's Kept NOTAMs live. The exported PDF's links (`interactiveLinks=false`) stay same-document anchors (`<a href="#ap-{icao}">`) into the detail sections `BuildFullNotamReportHtml` appends below the summary — `wkhtmltopdf` preserves internal anchor links, and there's no live app to call back into from inside a static PDF.
- **`FormatReportDate()`**: the header date (`"12AUG2026 1530CET"`) is formatted with `CultureInfo.InvariantCulture` — plain `DateTime.Now.ToString("ddMMMMyyyy HHmm")` with no culture rendered the month name in whatever the dispatcher's Windows locale is (French on this fleet, lowercase, e.g. `"12août2026"`), same convention now shared with the email subject/attachment date (`MainForm.Email.cs`'s `titleDate`). `ReportLegendAndRemarkHtml()` adds a small yellow-swatch legend (`"Yellow background = NOTAM active <24H"`, matching `AppendImpactRow`'s `bg="Yellow"` for an active-<24h row) and a one-line pointer (`"For Airport and NOTAM details, click on the NOTAM Ref or search the document."`) directly under the date, on both `Report()` (live) and `BuildFullNotamReportHtml()` (export) — shared so the two can't drift.

The AIP SUP report's header date reuses `FormatReportDate()` (`MainForm.Reports.cs`, same English-locale `"12AUG2026 1530CET"` fix) and has its own yellow-background legend (`"Yellow background = AIP SUP effective within 24H"`, matching the `bgcolor="Yellow"` already applied a few lines up to a SUP whose `fromDateInt <= tomorrowInt`) — same rationale as the NOTAM Report tab's, not shared code since the wording differs.

The AIP SUP report's Avio checkboxes are **CSS-styled `<div>`s**, not native `<input type="checkbox">` — native checkboxes render as tiny, blurry glyphs through `wkhtmltopdf` (a different rendering engine than the app's `WebBrowser` preview); the div-based version (coloured square + `&#10003;` checkmark, toggled by `updateCheckbox()`/`window.external.UpdateAviobook`) renders identically in both. `ExportToPdf` (`MainForm.Export.cs`) uses `--dpi 96` (not a much higher value) — PDF text is vector-drawn regardless of DPI, so a very high `--dpi` with no matching `--zoom` just shrinks all CSS-px-sized content (text, checkboxes) tiny and blurry on the page. It also passes `--enable-local-file-access` — newer `wkhtmltopdf` builds refuse to load `file://` subresources (the runway-diagram PNGs in `%TEMP%`, see below) that live outside the source HTML's own directory (`_export_temp.html` is written next to the exe) — but **this alone hasn't fixed it**: the sibling `airportDocu` project hit the identical wall with its ASL-logo `<img>` (correct `file://` URI + `--enable-local-file-access`, still missing from the PDF), so `ExportToPdf` now also redirects `wkhtmltopdf`'s stdout/stderr to `wkhtmltopdf_log.txt` next to the exe on every export — wkhtmltopdf reports exactly why a resource failed to load there, which is the next thing to check rather than guessing a third blind fix.

### Window resize doesn't auto-relayout the Filter/Station cards

The NOTAM Filter/Station right-column cards are absolute-positioned (not docked/anchored) and compute their width from `tabPage1.ClientSize.Width` **once, at render time** — widening the window after that leaves them stuck at the old width. `MainForm.cs`'s constructor wires `this.Resize` to a debounced (`_resizeDebounce`, 200ms `Timer`) call to `RefreshCurrentView()`, so a drag-resize re-renders once after the size settles rather than on every intermediate frame (which would also re-query the DB repeatedly).

### WebBrowser control runs in IE7 mode

The embedded `WebBrowser` renders in legacy IE quirks mode: **inline SVG is not supported** — use **VML** instead (`xmlns:v="urn:schemas-microsoft-com:vml"` + `v\:*{behavior:url(#default#VML)}`). Prefer `<table>`/`float` over modern fl/grid layout; `inline-block` is unreliable.

**Diagrams inside a small/compact, repeated-many-times layout should be raster, not VML** — every full-size diagram in this app (`BuildRwySvg`/`BuildRwySvgGeo`) sits inside a plain `position:relative` `<div>` (`.ahead`/`.diagram`), one per big card, and renders correctly. The Conflict tab's mini Not-ALTN-row diagram (`MainForm.Conflict.cs`) tried to reuse that same VML approach at a smaller scale, once per row (potentially many rows per page), and failed two different ways: with the VML-producing div inside a `<table>` `<td>` (lines/labels drifted into the neighboring cell's text — VML nested in a table cell escaping its intended local containing block), and again with a plain `position:relative`/`position:absolute` div pair copying `.ahead`/`.diagram` exactly (still drifted). Root cause not fully identified. Fixed by giving up on VML for this one diagram entirely: `BuildNotAltnMiniDiagram` always renders a plain raster `<img>` (`BuildRwyDiagramImageTagMini`, a `file://`-referenced PNG, `108×80`), even on the live tab where every other diagram in the report still uses VML — reusing the same raster+`file://` mechanism the NOTAM Report tab's own live `WebBrowser` preview already relies on (`BuildRwyDiagramImageTag`), proven to work with `DocumentText`-injected HTML. `RenderRwyDiagramPngMini` fills a **transparent** background (`Bitmap(..., PixelFormat.Format32bppArgb)` + `g.Clear(Color.Transparent)`), not a fixed color, since the row it sits in can be plain (`#fafbfb`) or yellow-tinted (`.h24`, `#fff8dc`). **If a future diagram needs to render compactly and repeatedly inside a tight layout, default to raster from the start.**
- **`.notamRow` is a `<table>` again (diagram `<td>` + main `<td>`), not the plain div pair tried in between** — once the diagram became a plain `<img>` (no more VML), the table-cell escape bug above no longer applied, and the table turned out to be the more reliable layout anyway: the div version's `padding-left` wasn't reliably reserving space for *wrapped* lines of NOTAM text in this WebBrowser control (only the first line was pushed clear of the diagram; later lines rendered underneath it). `table-layout:fixed` on both `.notamRow` and the nested `.rHeadTable`, plus no `white-space:nowrap` on `.rKeyPeriod` (which otherwise forced the row to the full pixel width of the longest key+period text, pushing the whole report wider than the WebBrowser control's viewport and forcing a horizontal scrollbar), keeps the row reliably within the page width regardless of content length.

### JavaScript ↔ C# Bridge (AIP SUP tab)

`Web_Sup_report` uses `ObjectForScripting = new AviobookScriptBridge(this)` so HTML checkboxes can call `window.external.UpdateAviobook(id)` directly into C# without redrawing the UI. The JS function `updateCheckbox(id, isYes)` updates only the affected checkbox in place.

### C# Version Constraint

Target is **.NET 4.0 / C# 4** (SharpDevelop portable). These are **not available**:
- `?.` null-conditional operator (use `x != null && x.Something`)
- `$""` string interpolation (use `string.Format` or concatenation)
- `nameof()`, `async/await`, LINQ on `ControlCollection` without `using System.Linq`

### Dynamic UI Controls

Controls created at runtime must have `Tag = "dispose"`. `ClearTaggedControls(panel)` (defined once, in `MainForm.AirportList.cs`; called from RWYs and NotamFilter too) removes and disposes them before redrawing. It handles `Label`, `TextBox`, `RichTextBox`, `CheckBox`, `Button`, `Panel`, `WebBrowser`, `DataGridView`, and `ComboBox` — **any new dynamic control type must be added to its `OfType<T>()` sweep**. This pattern is used in all tabs that rebuild their content (Filter, ICAO Notams, Airport List, RWYs).
